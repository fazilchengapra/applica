# Notifications App

## Purpose

Emits **in-app notification events** for the platform and publishes typed
events to AWS SNS for downstream services (analytics, search indexing).

> **The in-app inbox is not served here.** The `notifications` table, the five
> `/api/v1/notify` endpoints, and the realtime fan-out all live in
> `notification_service` (its own Postgres, via Prisma). This service is only a
> *producer*: it calls notification_service over HTTP. The Django model,
> `/api/v1/notify/push/`, and the Channels websocket were all removed on
> 2026-09-29 when the inbox moved — see that service's README.

## Endpoints

None. The former `POST /api/v1/notify/push/` was deleted along with the table it
wrote to; `notification_service` exposes the equivalent, and better-guarded,
`POST /api/v1/notifications/internal/notifications`.

## How this service creates a notification

`app/apps/notifications/services/create_and_push_notification.py`

`create_and_push(*, user, type, title, body, metadata=None)` keeps its original
name and signature, so the per-event helpers and their call sites are unchanged.
Internally it is a single authenticated HTTP POST:

```
POST {NOTIFICATION_SERVICE_URL}/api/v1/notifications/internal/notifications
X-Internal-Secret: <shared secret>
X-Internal-Service: user-service
{ "userId": 21, "type": "account.register", "title": "...", "body": "...", "metadata": {} }
```

It goes through Kong so the `internal-secret-auth` plugin verifies the secret on
the way in, and notification_service re-verifies it itself — two independent
checks on the same value.

**Failures are swallowed and logged, not raised.** Every caller is an auth flow
(phone verified, phone changed) running inside a transaction, and a notification
service outage must not roll back a successful verification. The cost is a lost
notification, which is recoverable; the alternative is a user who cannot verify
their phone number.

Realtime push is no longer this service's job: notification_service emits
`notification.created` to the websocket group after the insert commits.

## Realtime / WebSocket

Not here. Kong routes `ws/notifications/` to `notification_service`, which is
where the rows and the fan-out live. This service's Channels consumer was
removed with the model.

## Channels

| Channel | Mechanism | Status |
|---|---|---|
| In-app | notification_service table + its websocket | Implemented (moved 2026-09-29) |
| Email / SMS | Dispatched to `notification_service` via `/api/v1/notifications/internal/dispatch` | Implemented via dispatch + SNS |
| Push (mobile) | Only SNS event publishing; no FCM/APNs provider wired | Partial |

## Business rules / edge cases

- Notification failures are caught at the call site so a failed notification
  never turns a successful business operation into a 500 (per schema docs).
- PII in `metadata` is masked at this service layer (`app/apps/common/utils/mask`).
- Notification ids are UUIDs, generated by notification_service.

## Type vocabulary

`app/apps/notifications/constants/notification_type.py` is still the canonical
list of notification types this service may emit, and it is the only reason a
`models.py` survives in this app — as a comment pointing at the constants and
the new write path. notification_service validates incoming types against its own
copy of this list and rejects anything unknown with a `400`.

## Publishing to SNS

`app/apps/notifications/publishers/sns_publisher.py` publishes typed events
with `eventType` / `channel` attributes to `SNS_NOTIFICATIONS_TOPIC_ARN`.

## Dependencies

- Called by `authentication` flows (registration, password reset, phone OTP)
- Requires `NOTIFICATION_SERVICE_URL` / `NOTIFICATION_SERVICE_TIMEOUT` and the
  shared `GATEWAY_INTERNAL_SECRET`
- AWS SNS config for event publishing
